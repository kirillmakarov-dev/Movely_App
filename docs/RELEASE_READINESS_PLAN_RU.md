# План подготовки Movely к релизу

Дата оценки: 29 октября 2026 года. Рынок первого запуска: Израиль. Формат: адаптивный сайт для клиентов и перевозчиков.

Movely пока не готов к публичному коммерческому запуску. Уже есть основа интерфейса, серверная аутентификация и работа с заявками, но реальный вход, доставка SMS, рынок заявок, проверка перевозчиков и покупка доступа к контактам ещё не собраны в завершённый пользовательский процесс. Подготовка к релизу должна объединить продукт, визуальное оформление, доступность, приватность и эксплуатацию.

Этот документ — план работ и предлагаемые решения. Он не заменяет утверждённые продуктовые документы и не означает, что перечисленные изменения уже реализованы. Рекомендуемая граница первого релиза ниже требует синхронизации с существующим поэтапным планом перед разработкой.

## 1. Что уже есть и что действительно не хватает

Оценка основана на исходном коде, документах проекта, локальном просмотре главной страницы и формы заявки, проверке переключения языка и запуске существующих тестов. Публичное развёртывание, настоящие платежи, доставка SMS, реальные мобильные устройства и полная доступность не проверялись.

| Область | Текущее состояние | Вывод для релиза |
|---|---|---|
| Главная страница | Есть аккуратная светлая композиция, понятный основной призыв, блоки сценариев и адаптивные CSS-правила | Сохранить основу, доработать доверие, тексты, реальные состояния и мобильную проверку |
| Заявки клиента | Есть API черновиков, публикации, изменения, закрытия, отмены и версий; есть многошаговая форма | Проверить весь путь на реальной БД и в production-подобной среде |
| Вход | Интерфейс отправляет фиксированную строку `dev-google`; production Google verifier возвращает неподдерживаемую операцию | Обязательный блокер: подключить реальную проверку Google |
| SMS | Development sender пишет код в журнал; production sender ещё не реализован | Обязательный блокер: подключить провайдера и проверить доставку |
| Каталог и карточка заявки | Используют `mock-requests`; серверный MarketplaceModule пока пустой | Подключить реальные безопасные ответы API и правила доступа |
| Перевозчики, кошелёк, предложения | Ряд страниц содержит MoverPlaceholder; соответствующие серверные модули не реализуют коммерческий процесс | Для платного запуска нужны регистрация компании, проверка, баланс, покупка лида и возвраты |
| Фотографии | Форма сохраняет сведения о выбранных файлах в состоянии компонента; реальная загрузка не подключена | Завершить загрузку и защиту либо убрать этот шаг из первого релиза |
| Юридические страницы | Ссылки на условия, приватность и контакты в SiteFooter ведут в `#` | Создать настоящие страницы и рабочие каналы обращений |
| Возраст и согласия | В текущей модели пользователя нет записи возрастного подтверждения и версий принятых условий | Добавить серверное хранение и проверку правил, а не только галочки |
| Языки | Есть HE/EN; English при локальной проверке после перезагрузки оставался на иврите; перевод частично меняет DOM | Заменить на устойчивую локализацию; не показывать неработающий язык |
| Дизайн-система | Документ MASTER описывает фиолетовый акцент и Liquid Glass, фактический CSS — спокойную сине-белую тему | Привести спецификацию и компоненты к одному стилю |
| Тесты интерфейса | `npm test`: 15 из 15 не прошли; показанные ошибки связаны с английскими ожиданиями при ивритском интерфейсе | Исправить локализацию тестов, затем оценить поведение сценариев заново |
| Серверные тесты | После восстановления зависимостей: 65 прошли, 1 не прошёл, PostgreSQL-тесты исключены | Исправить слишком широкую проверку Web Storage и прогнать интеграционные тесты |
| Зависимости | Restore сообщил NU1902 и NU1903 для System.Security.Cryptography.Pkcs 9.0.0 | Обновить совместимую цепочку зависимостей и проверить применимость advisory |
| Документация | README описывает более раннюю готовность, чем фактическая реализация заявок | Синхронизировать статус и доказательства готовности |

Падение проверки Web Storage само по себе не доказывает хранение токенов в браузере: тест ищет строку `localStorage` во всех исходниках и срабатывает на настройке языка. Исправление должно сохранить проверку защиты сессий и отдельно разрешить безопасные пользовательские предпочтения.

## 2. Граница первого релиза

Рекомендуемый первый публичный продукт: клиент бесплатно создаёт заявку; проверенный перевозчик видит подходящие заявки, оплачивает доступ к конкретному контакту и связывается с клиентом; клиент может остановить поиск, пожаловаться и управлять данными.

Обязательный объём:

1. Реальная регистрация и возвращение в аккаунт.
2. Подтверждение возраста, условий и цели передачи контактов.
3. Два законченных сценария: переезд квартиры и перевозка отдельных вещей.
4. Рабочие черновики, публикация, изменение, отмена, закрытие и истечение срока.
5. Проверка перевозчиков и управление их доступом.
6. Реальный каталог с защитой адресов, телефонов и фотографий.
7. Для платного запуска — пополнение, учёт денег, атомарная покупка лида, квитанции и обработка возвратов.
8. Минимальная административная панель, обращения и блокировки.
9. Документы, доступность, мониторинг, резервные копии и проверенный откат.

Premium, подписки, внутренний чат, отзывы, сложный рейтинг, рекомендации, динамическую цену и приложение/PWA предлагается отложить. Если Premium остаётся обещанной возможностью релиза, его предложение, отказ клиента, запрет обхода отказа и уведомления становятся обязательными. Скрытые функции должны быть отключены и на сервере.

Разрешён отдельный закрытый пилот с ограниченным числом приглашённых участников и без оплаты. Он тоже требует настоящей защиты данных и понятных правил. Его нельзя представлять как готовый платный marketplace.

## 3. Регистрация и возраст

### Предлагаемая возрастная политика

Регистрация, публикация заявок и бизнес-аккаунты — с 18 лет, без верхнего возрастного ограничения. Просмотр информационных страниц не требует возраста или регистрации. Для несовершеннолетнего заявку создаёт взрослый от своего имени со своими контактами и ответственностью.

Это продуктовая рекомендация для сервиса с адресами, контактами и коммерческими отношениями. Закон Израиля определяет совершеннолетие с 18 лет и устанавливает особенности юридических действий несовершеннолетних; из этого не следует универсальный запрет любых сайтов для людей младше 18 лет. [Официальный текст закона о дееспособности и опеке](https://www.gov.il/BlobFolder/generalpage/guardian_080825/he/guardianlaw0725.pdf).

Не запрашивать полную дату рождения, паспорт, теудат-зеут или фотографию документа у обычного клиента только ради возрастного порога. Для MVP предложить явное подтверждение «Мне исполнилось 18 лет». Это самостоятельное заявление пользователя, а не доказанная проверка возраста. Дополнительную проверку проектировать только при обоснованном риске и с минимальным сбором данных.

При ответе «Нет» не создавать активный аккаунт и не публиковать заявку. Показать спокойное объяснение и возможность вернуться к справке. Не предлагать поставить ложную отметку. Предусмотреть процедуру обработки уже созданного аккаунта несовершеннолетнего: ограничение новых действий, проверка обращения и удаление данных с учётом необходимых правовых исключений.

### Поля регистрации клиента

| Поле | Когда требуется | Зачем |
|---|---|---|
| Имя для обращения | При создании аккаунта | Представление клиента перевозчику и поддержка; не требовать сложного формата имени |
| Телефон | Перед публикацией | Проверка владения номером и связь по заявке |
| Код из SMS | При подтверждении номера/входе по телефону | Подтверждение доступа к номеру |
| Подтверждение 18+ | До завершения регистрации | Правило допуска к регистрации |
| Принятие условий | До завершения регистрации | Фиксация условий обслуживания |
| Уведомление о приватности | До сбора соответствующих данных | Объяснение целей, получателей и прав |
| Email | Необязателен для основного клиентского сценария | Копии уведомлений и восстановление, если эти функции реально есть |
| Язык | По выбору пользователя | Понятные страницы, SMS и помощь |
| Рекламная подписка | Только по отдельному выбору | Маркетинговые сообщения; по умолчанию выключена |

Не спрашивать при регистрации домашний адрес, профессию, пол, семейное положение, доход, состояние здоровья и состав семьи. Адреса нужны внутри конкретной заявки. Полное имя собирать только в той мере, в какой оно требуется сценарию; не превращать форму клиента в анкету проверки личности.

Google должен быть удобным вариантом, а не единственным понятным способом доступа. В качестве улучшения доступности предлагается вход по подтверждённому телефону без обязательного аккаунта Google. Это расширение текущего решения Google + SMS: перед реализацией описать связывание аккаунтов, повторную выдачу телефонных номеров, смену номера и безопасное восстановление доступа.

### Регистрация перевозчика

Сначала телефон, имя представителя, 18+ и принятие условий. Затем название бизнеса, статус бизнеса, идентификационные реквизиты в необходимом объёме, контакт ответственного, регионы работы и типы перевозок. Документы для проверки — отдельным защищённым процессом с объяснением цели, доступа и хранения.

Проверить полномочия представителя. Чётко разделить статусы «Проверка не завершена», «Проверен», «Нужны сведения», «Отклонён», «Приостановлен». До проверки не открывать контакты клиентов. Значок «Проверен» должен объяснять, что именно проверено и когда; он не должен автоматически означать страхование, гарантию качества или государственную лицензию.

### Как записывать подтверждения

Хранить на сервере идентификатор пользователя, тип подтверждения, версию текста, язык, дату и время UTC, источник действия. Отдельно фиксировать принятие условий, подтверждение возраста, разрешение передачи контактов в рамках заявки и рекламную подписку. Для последней хранить также отзыв согласия. IP и сведения об устройстве сохранять только при обоснованной необходимости и ограниченном сроке.

Не считать сам вход через Google принятием правил Movely. Не отмечать галочки заранее. При существенном изменении условий сохранять предыдущие версии и повторно получать необходимое подтверждение. Публикация через прямой вызов API должна отвергаться, если обязательные условия не выполнены.

## 4. Политика конфиденциальности

До выпуска заполнить фактические данные оператора: юридическое имя, реквизиты и адрес, рабочий контакт по приватности, поставщики, страны обработки, сроки хранения и порядок обращений. Эти сведения нельзя заменить вымышленными реквизитами или обещанием «добавим позже».

Израильское уведомление при сборе данных должно объяснять цель, обязательность или добровольность передачи и последствия отказа, получателей и цели передачи, владельца контроля над данными и способы связи, права доступа и исправления. Краткое объяснение нужно показывать в момент сбора, со ссылкой на полный документ. [Рекомендации PPA по обязанности информирования](https://www.gov.il/BlobFolder/legalinfo/duty_to_notify/he/notify13.pdf).

Политика должна описывать реальные процессы Movely:

1. **Какие данные:** аккаунт Google в объёме разрешённого профиля, имя, телефон, заявки, адреса, даты, фотографии, бизнес-документы, обращения, платежные события и необходимые технические журналы.
2. **Цели:** организация контакта по переезду, обслуживание аккаунта, проверка компаний, предотвращение злоупотреблений, платежи, поддержка; улучшение продукта и реклама выделены отдельно.
3. **Кому доступны данные:** оператор, сотрудники с соответствующей ролью, авторизованные перевозчики, хостинг, SMS и платёжные поставщики; отдельно определить правовую роль перевозчика после получения контакта.
4. **Как работает продажа лида:** перевозчик платит за доступ к контактам по конкретной заявке. Нельзя одновременно обещать пользователю «мы никогда не передаём/не продаём ваши данные» без точного объяснения этой модели.
5. **Когда открываются контакты:** только после разрешённой сервером операции; заранее объяснить предел числа получателей и перечень раскрываемых данных.
6. **Фото и свободный текст:** можно случайно раскрыть детей, документы, номер квартиры, ценные вещи, лица и геолокацию. Нужны подсказки, удаление метаданных и контролируемый доступ.
7. **Хранение и удаление:** сроки по категориям, основания исключений, резервные копии и исторические версии заявок.
8. **Права и обращения:** просмотр и исправление данных, отзыв необязательных согласий, обращение об удалении и понятное объяснение того, что необходимо сохранить.
9. **Cookies и внешние сервисы:** действительные категории, поставщики, сроки и настройки; без универсального списка сервисов, которые сайт не использует.
10. **Международная обработка:** страны хранения, поставщики и условия передачи, если данные выходят за пределы Израиля.
11. **Несовершеннолетние:** правило 18+, действия при выявлении неподходящего аккаунта и канал обращения представителя.
12. **Обновления:** номер версии, дата действия и уведомление о существенных изменениях.

Отдельный обязательный пункт правовой проверки: модель продажи доступа к лидам может затрагивать специальные обязанности для баз, предназначенных для передачи информации третьим лицам за плату. Проверить применимость регистрации базы и назначения DPO по характеру деятельности и объёму данных. Поправка 13 не означает, что любая небольшая компания обязана автоматически назначать DPO. [Официальные вопросы и ответы PPA по поправке 13](https://www.gov.il/he/pages/tikun13_qa?chapterIndex=6).

### Уведомление непосредственно перед публикацией

Предлагаемый смысл короткого текста:

> После публикации проверенные перевозчики смогут увидеть описание переезда. Ваше имя, телефон и точные адреса получат только перевозчики, которым разрешён доступ по этой заявке, — не более указанного ниже количества. Они могут связаться с вами по поводу этого переезда. Публикация бесплатна. Остановить новые обращения можно в разделе «Мои заявки».

Рядом показывать актуальный лимит из серверной настройки, по текущей спецификации — обычно до трёх перевозчиков. Зафиксировать предел для конкретной публикации; не увеличивать его молча после согласия пользователя. Отдельно объяснить: остановка поиска прекращает новые продажи доступа, но не удаляет уже полученные перевозчиками копии контактов.

Для осознанного подтверждения можно использовать отдельный непредустановленный пункт о передаче контактов в рамках заявки. Он не должен давать разрешение на рекламу, перепродажу базы или бессрочные обращения по другим поводам.

### Предлагаемый график хранения

Ниже рабочие продуктовые значения для последующей правовой и технической проверки, а не установленные законом сроки:

| Категория | Предлагаемая настройка | Действие |
|---|---|---|
| Неотправленный черновик на общем устройстве | Текущая сессия; более долгое сохранение только осознанно | Не оставлять адреса и телефоны в постоянном Web Storage без необходимости |
| Неактивный серверный черновик | 30 дней с последнего изменения | Предупреждение, затем удаление при отсутствии иных оснований |
| Закрытая заявка и бытовые фото | 90 дней после закрытия как исходный вариант | Удаление/обезличивание, кроме конкретного спора или иной обоснованной обязанности |
| Документы проверки компании | Минимальный период проверки и необходимого подтверждения результата | По возможности хранить результат вместо постоянной копии документа |
| Журналы доступа и безопасности | Срок по классификации базы, применимым правилам безопасности и расследованиям | Минимизировать данные, ограничить доступ и задать автоматическую очистку |
| Финансовые документы | По требованиям применимого бухгалтерского и налогового права | Не удалять только из-за закрытия аккаунта; ограничить дальнейшее использование |
| Резервные копии | Например, скользящее окно 30 дней после проверки требований | Удаления должны применяться вновь после восстановления |

Удаление охватывает текущие данные, версии заявок, фотографии, CDN, поиск, выгрузки и сервисы обработки. Не обещать мгновенное удаление всех копий. Историческая покупка лида по текущей спецификации сохраняется после закрытия заявки, но это не должно автоматически превращаться в бессрочный доступ ко всем персональным данным. Установить конечный срок и документировать изменение бизнес-правил.

## 5. Условия использования и правила сайта

Подготовить юридический комплект с короткими пояснениями простым языком. Финальные формулировки проверить у специалиста по израильскому праву до публичного запуска; юридический статус оператора и платёжная модель ещё должны быть заполнены фактическими данными.

| Документ / страница | Что включить |
|---|---|
| Условия использования | Оператор, 18+, роли сторон, аккаунт, публикация, изменение правил, прекращение доступа, обращения и споры |
| Правила клиентов | Достоверность заявки, право заказывать перевозку имущества, отсутствие чужих данных без основания, актуальность даты и контакта |
| Условия перевозчиков | Проверка компании, разрешённое использование контактов, запрет перепродажи/спама, цены, качество информации, нарушения и апелляция |
| Правила лидов и возвратов | Что именно покупается, лимит покупателей, сумма, налоги, ошибки списания, недействительные лиды, сроки и способ обращения |
| Политика конфиденциальности | Реальная схема обработки данных и права пользователя |
| Cookies и настройки приватности | Обязательные функции, аналитика, маркетинг, поставщики и возможность изменения выбора |
| Заявление о доступности | Проведённые проверки, известные ограничения, контакт для помощи и дата обновления |
| Помощь и контакты | Как оформить/отменить заявку, что делать без SMS, кто отвечает за переезд, как пожаловаться |

Объяснить различие: публикация заявки не является подтверждённым бронированием перевозки; покупка лида не гарантирует заказ; выражение интереса, если оно будет реализовано, не означает оплату или договор. Указать, кто согласует конечную цену, отвечает за перевозку, повреждения, страховку и документы. Не обещать освобождение Movely от любой ответственности.

Запретить мошенничество, фиктивные заявки, угрозы, дискриминационные и оскорбительные материалы, незаконные перевозки, публикацию чужих контактов, сбор данных ботами, перепродажу лидов и рекламные рассылки по купленным телефонам. Предусмотреть жалобу, проверку, соразмерное ограничение и возможность обжалования.

Разделить отмену поиска клиентом, отмену самой перевозки и возврат платежа за лид: это разные отношения. Правила возврата денег или кредита кошелька, неиспользованного остатка и подписки проверить отдельно; кредит в кошельке не может автоматически заменять денежный возврат, если по применимому праву требуется другой способ.

Блокировка жалобщиком или модератором должна пресекать новые взаимодействия по правилам безопасности. Отказ от предложения, если Premium включён, нельзя обходить покупкой контакта. Нужно учитывать, что уже увиденный номер невозможно технически «забыть» на чужом устройстве: здесь необходимы правила использования и работа поддержки.

## 6. Политика улучшения сайта и аналитика

Предлагаемая политика улучшений: собирать минимальные события о работоспособности и прохождении шагов, объяснять цель и отключать необязательные инструменты до соответствующего выбора пользователя. «Улучшение сервиса» не является безграничным разрешением использовать любые данные для любых целей.

1. Отделить обязательные сессионные механизмы и безопасность от необязательной продуктовой аналитики и маркетинговых пикселей.
2. Если используются необязательные cookies/идентификаторы, предоставить равно понятные варианты «Принять необязательные», «Отклонить необязательные», «Настроить». Отказ не должен ломать заказ услуги.
3. Доступность настройки сохранить в подвале и аккаунте. Перед выбором проверить сетевые запросы: баннер не заменяет реальную блокировку трекеров.
4. Не отправлять имена, телефоны, адреса, фото, SMS-коды, свободный текст и идентификаторы доступа в аналитику, URL или отчёты об ошибках.
5. На старте не включать запись пользовательских сессий на формах с персональными данными. Если позже понадобится исследование, отдельно спроектировать маскирование и согласие; проверить его тестами.
6. Не включать использование личных данных для обучения ИИ по умолчанию. Для новой цели нужен отдельный анализ, прозрачное уведомление и необходимые разрешения.
7. Предложить кнопку «Сообщить о проблеме» без обязательной отправки скриншота. На скриншотах предупредить о возможных личных данных.
8. Еженедельно разбирать ошибки, обращения, места ухода из формы и время до первого контакта; ежемесячно проверять доступность и документы после изменений.

Ключевые показатели: начало заявки → просмотр итогов → подтверждение телефона → успешная публикация; время заполнения; ошибки по шагам; доставка SMS; обращение в поддержку; время до первого контакта перевозчика; возвраты и жалобы. Измерять подтверждённые сервером действия, а не только клики. Цели по конверсии уточнить после пилота, не выдумывать текущие показатели.

## 7. Визуальное оформление

Сохранить спокойную сине-белую основу. Для Movely приоритетны читаемость, уверенность и понятные действия. Главная уже выглядит организованной; наиболее полезна последовательная доработка всех состояний и страниц.

1. Утвердить один набор цветов, размеров шрифта, отступов, радиусов, границ и теней. Обновить MASTER под реальный интерфейс и применять общие компоненты.
2. Основной текст ориентировочно 18 px, не менее 16 px в обычных полях; пояснения достаточно крупные и контрастные. Проверить настоящий шрифт иврита: сейчас CSS называет Noto Sans Hebrew, но показанный layout загружает Atkinson только с latin.
3. Уменьшить вертикальную высоту вступления формы: на проверенном экране шаги занимают значительную часть первого экрана, сами поля находятся ниже.
4. На главной оставить основной путь «Нужна перевозка» и отдельно «Я перевозчик». Каталог работ не должен выглядеть обязательным этапом для клиента.
5. Сделать два наглядных сценария с простыми иллюстрациями квартиры и отдельных вещей, короткими примерами и одинаковой композицией карточек.
6. Добавить реалистичную иллюстрацию или лицензированное фото перевозки, если это помогает объяснению. Не использовать случайные фото чужих бригад как доказательство собственных услуг.
7. Отдельно оформить доверие: кто оператор, как проверяются перевозчики, кто видит телефон, сколько компаний сможет обратиться, как остановить поиск.
8. Не показывать придуманные отзывы, рейтинги, число клиентов, старые даты и фиктивное «12 минут назад». Главная сейчас использует демонстрационные августовские заявки; заменить реальными данными или явно подписанным примером.
9. Оформить состояния загрузки, пустого списка, ошибки, успешной публикации, истечения сессии, недоступного сервера, отсутствующего результата и закрытой заявки.
10. Подготовить favicon, превью ссылок, логотип на светлом/тёмном фоне и единый набор иконок с текстовыми подписями.
11. Протестировать 320, 375, 390, 768, 1024 и 1440 CSS px, альбомную ориентацию, увеличение текста и длинные переводы.
12. Не добавлять анимации, параллакс и прозрачные панели ценой контраста и скорости; сохранить поддержку reduced motion.

Критерий готовности: пользователь видит следующий шаг, понимает цену/бесплатность и последствия действия, не ищет помощь в техническом тексте и не принимает пример за настоящий заказ.

## 8. Удобство для неопытных и пожилых пользователей

Понятный интерфейс должен быть базовым. Не требовать выбрать «режим пенсионера» или раскрыть возраст, инвалидность и компьютерные навыки.

### Форма заявки

Предлагаемая структура из шести понятных групп с короткими условными подшагами:

1. Что перевозим: квартира или отдельные вещи.
2. Откуда и куда: города, адреса и доступ к подъезду.
3. Что нужно перевезти: комнаты, вещи и дополнительные услуги по выбранному сценарию.
4. Когда: дата, гибкость, время и необязательный бюджет.
5. Проверка сведений: редактирование, необязательные фотографии и заметки.
6. Подтверждение аккаунта и телефона, понятное раскрытие контактов, публикация.

Не объединять десять нынешних шагов в шесть длинных перегруженных форм. Цель — снизить нагрузку: компактный прогресс, один текущий вопрос/блок, дополнительные поля только по необходимости.

Обязательные улучшения:

- Не заставлять повторно выбирать квартиру после перехода по кнопке «Переезд квартиры».
- Одна основная кнопка на шаг: «Продолжить», «Проверить заявку», «Опубликовать бесплатно»; рядом понятная «Назад».
- Возврат не очищает введённое. Переключение языка, вход и открытие условий не должны терять заявку.
- Сохранение должно быть настоящим: различать «Введено на этом устройстве», «Сохраняем», «Сохранено», «Не удалось сохранить».
- Для анонимного пользователя предусмотреть сохранение на время перехода во вход без бессрочного хранения адресов на общем устройстве. Чётко предупреждать о потере несохранённого при закрытии вкладки.
- Для бюджета, веса, количества коробок и других оценочных сведений добавить «Не знаю» там, где отсутствие значения допустимо. Не подменять «не знаю» нулём.
- Постоянные подписи над полями, примеры формата, единицы измерения и отметка необязательных полей.
- Ошибка рядом с полем объясняет исправление; длинная форма также содержит краткий список ошибок с переходами к полям.
- Неподвижные кнопки не перекрывают экранную клавиатуру, ошибки и последнюю строку.
- Поле SMS-кода поддерживает вставку и автозаполнение; есть «Изменить номер», повторная отправка с понятным ожиданием, обработка просрочки и канал помощи.
- Убрать из пользовательского текста API, object storage, Phase 5, dev-google, OTP и «серверный DTO». Писать «код из SMS», «заявка», «телефон пока скрыт».
- После публикации показать номер заявки, следующий шаг, кто может связаться, кнопки просмотра/изменения/закрытия и помощь.

### Помощь

Сделать заметную ссылку «Нужна помощь?» в постоянном месте. Указать настоящий канал, часы и реалистичный срок ответа. Если доступна помощь оператора по телефону, он не должен просить пароль Google или SMS-код; ввод и подтверждения остаются у клиента. Подготовить короткие текстовые инструкции со скриншотами; видео только дополнительное, с субтитрами.

### Доступность

Целевой технический уровень — WCAG 2.2 AA; применимость и актуальную редакцию израильского стандарта SI 5568 и сервисных правил проверить отдельно. Это разные уровни определения требований. [Руководство Израиля по доступности сайтов](https://www.gov.il/he/pages/website_accessibility?chapterIndex=6), [WCAG 2.2](https://www.w3.org/TR/WCAG22/).

Проверить клавиатуру, видимый фокус, порядок чтения, возврат фокуса после модальных окон, подписи, сообщения для скринридера, контраст обычного текста 4.5:1, увеличение текста до 200%, перестроение контента и отсутствие зависимости только от цвета. Кнопки 44–48 px — предлагаемый более удобный стандарт Movely; это не утверждение, что минимум WCAG 2.2 AA всегда равен 44 px.

На иврите проверить RTL, направление стрелок, телефон и SMS-код слева направо, валюту, даты и смешанные строки. Для языков использовать словари и стабильное состояние, а не замену текста через MutationObserver. Иврит должен быть полностью готов; английский и русский — только после полного перевода сценариев, ошибок, SMS, помощи и документов. Если язык не готов, скрыть выбор до его выпуска.

## 9. Защита данных и техническая готовность

1. Реальная аутентификация Google с серверной проверкой токена, получателя и срока; настоящий SMS-провайдер. Production не должен принимать development credentials или возвращать отладочные коды.
2. Удалить заранее заполненный демонстрационный телефон. Не записывать OTP, токены и полные персональные данные в production-логи.
3. Выбрать схему развёртывания web/API. Предпочтителен единый origin с проксированием API. Если origin разные, отдельно проверить credentialed CORS, cookie, CSRF и доверенные proxy-заголовки: сейчас frontend отправляет credentials, а CORS в Program.cs не включает AllowCredentials.
4. Production-конфигурация должна завершать запуск с ошибкой при отсутствии обязательных секретов/адреса БД/провайдеров, вместо локальных значений по умолчанию.
5. Проверка прав на каждую заявку, версию, фото, покупку и административное действие. Пользователь А не должен получать данные Б заменой идентификатора.
6. Разделить безопасную карточку и приватный ответ. До разрешения контакты отсутствуют в API, HTML, frontend-состоянии, логах, метаданных, кэше и выгрузках.
7. Сейчас ограничитель OTP живёт в памяти процесса и использует сочетание телефона с IP. Для production нужны независимые пределы по номеру/IP/аккаунту, защита бюджета SMS и согласованные счётчики между экземплярами сервера.
8. Закрытое хранилище фото, ограниченные по времени ссылки, проверка реального типа файла, размера и количества; безопасное преобразование изображений и удаление EXIF. Не принимать пользовательский objectKey без проверки владельца.
9. MFA для администраторов, минимальные права, журнал просмотра контактов и изменений статуса, обоснование ручных финансовых операций.
10. TLS, проверенные security headers, CSP, защита от CSRF/XSS, безопасные cookies и ограничения времени сессии. Проверить выход со всех устройств, смену телефона, удаление аккаунта и восстановление.
11. Проверить npm/NuGet-зависимости и обновить уязвимую цепочку System.Security.Cryptography.Pkcs. Найденные предупреждения связаны с опубликованными advisory по отказу в обслуживании; наличие уязвимого пакета ещё не доказывает достижимую эксплуатацию в Movely. [Microsoft advisory, высокая серьёзность](https://github.com/advisories/GHSA-846f-f764-76mx), [Microsoft advisory, умеренная серьёзность](https://github.com/advisories/GHSA-2fmv-rv2c-59x7).
12. Отдельные development/staging/production, разделённые базы и аккаунты провайдеров. Не копировать реальные адреса и телефоны в тестовую среду без необходимых мер.

## 10. Деньги и доступ к лидам

Для коммерческого запуска эти действия должны работать как одна защищённая операция: проверить перевозчика → проверить состояние заявки → проверить лимит → проверить остаток → списать средства → создать покупку → открыть контакты → занять одно место.

Критерии:

- Повторный клик и сетевой повтор не вызывают повторное списание.
- Два одновременных покупателя последнего места не получают оба успешную покупку.
- При любой ошибке нет состояния «деньги списаны, доступ не выдан».
- Цена и валюта берутся с сервера, а фактически уплаченная цена сохраняется в покупке.
- Доступ нельзя получить к отменённой/закрытой заявке или в обход запрета для конкретного перевозчика.
- Баланс строится по проверяемому журналу операций, а не вручную изменяемой цифре.
- Пополнение подтверждается сервером платёжного провайдера: подпись webhook, защита от повтора и сверка суммы обязательны.
- Реквизиты банковской карты не хранятся в Movely; использовать подходящий hosted checkout/tokenization и проверить договорные обязанности.
- Возврат имеет статус, причину, решение и трассируемую операцию. Повторное решение не создаёт второй возврат.
- До оплаты показать, что это доступ к контакту, количество возможных конкурирующих покупателей, итоговую стоимость и правила возврата.
- Для новых Premium-подписок отдельно понадобятся явное согласие на автопродление, цена/период, отмена и уведомления; до реализации подписку не продавать.

## 11. Поддержка, эксплуатация и обнаружение сайта

До пилота назначить ответственных по функциям: продукт, разработка, дизайн/контент, QA/доступность, операции/поддержка и право/приватность. Один человек может выполнять несколько ролей, но у каждой очереди обращений должен быть владелец.

Обязательные возможности администрации: проверка компании, приостановка аккаунта, снятие опасной заявки, обработка жалобы, возврат, поиск обращения и журнал действий. В служебных списках маскировать контакты до необходимого просмотра. Настройки цены и лимита покупателей защищать и версионировать.

Эксплуатация:

- Автоматический выпуск через CI с проверками и ручным решением о запуске подготовленной версии.
- Проверенная миграция на чистой и уже заполненной PostgreSQL, план совместимости и отката.
- Readiness проверяет необходимые зависимости; текущий `/health` возвращает healthy без проверки базы.
- Зашифрованные резервные копии и пробное восстановление в отдельную базу. Предлагаемые цели пилота: RPO до 24 часов, RTO до 4 часов; для платного продукта ужесточить по цене потери операций и возможностям point-in-time recovery.
- Мониторинг ошибок API, публикации, SMS, платежей и задач очистки; оповещения о росте отказов и расхода SMS.
- Инструкция инцидента: остановка опасной функции, ограничение доступа, сохранение необходимых доказательств, оценка обязанностей уведомления и информирование пользователей.
- Контролируемое отключение публикации/покупок при аварии, без потери данных и повторных списаний.
- Рабочая поддержка, шаблоны ответов и понятные сроки: предлагаемый первый ответ в течение рабочего дня; срочные угрозы и утечки — немедленная эскалация ответственному.

Обнаружение сайта и контент:

- Домен, HTTPS, канонические URL, заголовки и описания публичных страниц, favicon и актуальное превью ссылки.
- Sitemap только для предназначенных к индексации страниц. Кабинет и приватные заявки защищаются авторизацией; robots/noindex не заменяют защиту.
- Закрыть staging от посторонних и поисковиков. Проверить 404, 500, недоступный API, неверную ссылку и устаревшую заявку.
- Страницы «О сервисе», «Как это работает», «Помощь», «Контакты» с фактической информацией.
- При подключении email настроить отправителя, SPF/DKIM/DMARC и обработку недоставки.
- Все картинки и шрифты должны иметь подходящие права использования.

## 12. Проверки перед запуском

### Автоматические

1. Исправить 15 UI-тестов: задавать язык явно, проверять доступные названия и пользовательское поведение. Не превращать тесты в формальную замену английских строк без проверки сценариев.
2. Исправить серверную проверку Web Storage: запрещать хранение секретов, сохранив допустимую настройку языка.
3. Прогнать build/lint/typecheck, backend-тесты и реальную PostgreSQL-интеграцию в воспроизводимом CI.
4. Добавить браузерный сквозной тест нового клиента: заполнение → вход → SMS → согласия → публикация → просмотр в кабинете → закрытие.
5. Добавить сквозной тест проверенного перевозчика: вход → каталог → покупка → однократное списание → разрешённый контакт.
6. Проверить отрицательные сценарии: недопустимый возраст, непринятые правила, неверный/просроченный код, превышение лимита, чужой объект, повторный платёж, отказ провайдера, закрытая заявка, удалённый файл.
7. Проверить удаление по всем хранилищам и версиям, восстановление из backup с повторным применением удаления, отсутствие личных данных в аналитике и логах.
8. Выполнить автоматический аудит доступности и отдельно ручные проверки; балл Lighthouse не является сертификатом доступности или юридического соответствия.

### Ручные

Провести минимум два раунда с 8–12 участниками суммарно: молодые взрослые, 40–60, 65+, люди с низкой цифровой грамотностью и участники, использующие вспомогательные технологии. Это исследование удобства, а не статистическое доказательство пригодности для всех.

Без подсказок модератора попросить: создать небольшую перевозку, исправить адрес, восстановиться после неправильного кода, объяснить кто увидит телефон, остановить поиск, найти помощь и настройки данных. Проверять настоящие мобильные Safari/Chrome, настольные Chrome/Edge/Firefox и хотя бы NVDA/VoiceOver на ключевых сценариях.

Предлагаемые критерии пилота:

- Не менее 90% участников завершают основной сценарий без вмешательства; при малой выборке обязательно учитывать отдельные неудачи старших и неопытных пользователей.
- Никто не публикует заявку или не подтверждает передачу контактов, ошибочно считая действие сохранением черновика.
- Пользователи могут объяснить, кто получит контакты и как прекратить новые обращения.
- Нет потери введённого при обычном возврате, повторе после сетевой ошибки и завершении входа.
- Нет критических препятствий клавиатуры, чтения или увеличения текста.
- Время заполнения измерено отдельно для двух типов перевозки; обещание «за несколько минут» согласуется с результатами.

Для производительности установить бюджет и измерить ключевые страницы на слабом телефоне и медленной сети. Рабочие цели: LCP ≤ 2.5 с, INP ≤ 200 мс, CLS ≤ 0.1 на 75-м перцентиле реальных посещений после накопления данных. До запуска — лабораторные проверки как предварительная оценка, без заявления о подтверждённых полевых метриках. [Официальные ориентиры Core Web Vitals](https://web.dev/articles/vitals).

## 13. Порядок выполнения и контрольные результаты

P0 — блокирует выпуск с реальными данными/деньгами. P1 — требуется для качественного публичного запуска. P2 — улучшение после подтверждения основного процесса. Отсутствие функций, исключённых из первого релиза, не считается P0, если они отключены и не обещаются.

| Этап | Приоритет | Работы | Ответственный | Зависимость | Проверяемый результат |
|---|---|---|---|---|---|
| 1 | P0 | Сверить текущие фазы, определить состав релиза, карту данных, оператора, получателей, хранение и правило 18+ | Продукт + право/приватность + tech lead | Нет | Одна согласованная спецификация вместо противоречащих статусов |
| 2 | P0 | Реальные Google/SMS, конфигурация web/API, сессии, восстановление, возраст и версии согласий | Backend + frontend | 1 | Новый пользователь входит и публикует только после всех проверок |
| 3 | P0/P1 | Надёжные заявки, фото или исключение фото, упрощённая форма, языки, кабинет | Full stack + дизайн | 1–2 | Оба типа заявок проходят целиком, данные не теряются |
| 4 | P0 | Каталог реальных заявок, перевозчики, проверка компаний, безопасные DTO | Backend + frontend + операции | 2–3 | Контакты недоступны неавторизованному перевозчику |
| 5 | P0 для платного запуска | Кошелёк, платежи, покупка, возвраты и минимальная администрация | Backend + платежи + QA | 4 | Конкурентные и повторные операции не нарушают деньги и лимиты |
| 6 | P0/P1 | Рабочие документы, настройки данных, поддержка, визуальная согласованность и доступность | Контент + право + дизайн + QA | Начать после 1, завершить после 3–5 | Все обещания соответствуют продукту, нет пустых ссылок |
| 7 | P0 | Тесты, уязвимые зависимости, PostgreSQL, production build, CI, мониторинг, backup и восстановление | Tech lead + QA + DevOps | 2–6 | Проверяемая готовность staging и процедура отката |
| 8 | P0/P1 | Закрытый пилот и два раунда usability, исправление критических проблем | Продукт + QA + поддержка | 7 | Успешный путь клиента и перевозчика на реальных устройствах |
| 9 | P1 | Ограниченный запуск по регионам/числу компаний, наблюдение, постепенное расширение | Продукт + операции | 8 | Есть реальное предложение перевозчиков, ошибки и жалобы управляемы |
| 10 | P2 | Premium, отзывы, чат, расширенная аналитика, другие языки и PWA | Продукт + разработка | Стабильный основной сценарий | Улучшения подтверждены спросом, сохранена защита данных |

Сопоставление с существующим планом: идентификация — Phase 2; заявки/форма — 3–4; каталог/бизнес — 5–6; деньги и лиды — 7–8; Premium — 9 при включении; кабинет — 10 в необходимом объёме; возвраты/администрирование — 11–12; безопасность/production — 13–14. Предлагаемое исключение Premium меняет зависимости, поэтому сначала обновить план и decision log, затем реализовывать.

Фиксированную дату релиза пока не назначать: отсутствуют целые коммерческие модули, не только полировка. Оценку трудозатрат составить по этим этапам после определения платёжного и SMS-провайдера, состава команды и границы MVP. Закупка услуг и ожидание проверок провайдеров учитываются отдельно от разработки.

## 14. Условия допуска к публичному релизу

- [ ] Нет тестового входа, отладочных кодов и демонстрационных заявок, выдаваемых за реальные.
- [ ] В production работают вход, SMS и повторный доступ к аккаунту.
- [ ] Возрастное правило, условия и раскрытие контактов проверяются сервером и фиксируются по версиям.
- [ ] Работают обе формы, сохранение, публикация, редактирование и закрытие.
- [ ] Контакты и точные адреса не выдаются до авторизации, включая фотографии и версии заявки.
- [ ] Для коммерческого запуска подтверждены однократные платежи, покупки и возвраты.
- [ ] Нет неработающих элементов навигации и неподдерживаемых обещаний.
- [ ] Документы содержат реальные реквизиты, процессы и действующие контакты; правовые вопросы закрыты профильной проверкой.
- [ ] Пользователь может получить помощь, исправить данные, отозвать необязательное согласие и запросить удаление.
- [ ] Пройдены автоматические проверки, PostgreSQL-интеграция и ручные сценарии доступности.
- [ ] Критические проблемы безопасности исправлены; по остальным есть владелец, решение и срок.
- [ ] Резервная копия действительно восстановлена, миграции и откат отрепетированы.
- [ ] Есть ответственные за жалобы, сбои, платежи, приватность и поддержку.
- [ ] Пилот подтвердил понятность сайта для старших и неопытных пользователей.
- [ ] В регионах запуска есть проверенные перевозчики; реклама не приводит клиентов в пустой marketplace.
