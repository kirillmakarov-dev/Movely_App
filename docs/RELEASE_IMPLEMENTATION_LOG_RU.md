## 4. Мобильная форма и сохранность черновиков

Реализовано 2026-10-29:

- Вместо десяти постоянно видимых кнопок шагов — текущий шаг и раскрываемая навигация. После перехода фокус попадает на заголовок нового шага.
- Дополнительные сведения о подъезде раскрываются по запросу. В короткой перевозке адреса и сведения о доступе больше не повторяются в обоих шагах.
- Добавлены доступные состояния выбранных вариантов, семантика progressbar и подсказки автозаполнения адреса.
- Анонимный пользователь может явно включить сохранение текстового черновика в текущей вкладке (sessionStorage, до 24 часов после последнего обновления). До выбора ничего не сохраняется в браузерное хранилище.
- Перед включением объясняется, что сохраняются адреса и заметки, и что это не рекомендуется на общем компьютере. Файлы, имена файлов, OTP, данные авторизации и серверные идентификаторы не сохраняются.
- При восстановлении проверяются версия, срок, размер и структура. Повреждённые данные отбрасываются; недоступное хранилище показывает предупреждение вместо ложного сообщения об успехе.
- Снятие выбора, вход, выход, успешная публикация и начало новой заявки очищают локальную копию. При выходе также очищаются поля текущей формы.
- Добавлено предупреждение браузера перед уходом с несохранёнными изменениями; доступность такого диалога зависит от браузера, особенно на телефонах.
- Во время запросов сохранения поля и переходы блокируются, чтобы ответ сервера не затёр параллельные изменения.
- Перед публикацией обязательно сохраняются последние значения, даже если пользователь перешёл к публикации напрямую через навигацию.
- Убрана неработающая имитация выбора фотографий: отображается честное сообщение о недоступности загрузки.

Проверка:

- Web: 26/26 тестов; в том числе восстановление после повторного открытия компонента, выключение сохранения, срок жизни, повреждённая структура, исключение секретов/файлов, отказ хранилища и порядок save → publish.
- API: 66/66 без PostgreSQL integration. Статическая проверка хранения ограничивает sessionStorage единственным адаптером анонимных черновиков; в остальном production-коде browser storage запрещён.
- Общий lint, TypeScript и Next production build: успешно.
- Браузер: 320/390px без горизонтального переполнения, переход с фокусом на новый заголовок, восстановление введённого города и текущего шага после reload.

Осталось: свести процесс к шести смысловым группам, завершить полевую валидацию и серверные согласия, подключить настоящие загрузки и production auth. Текущая компактная навигация не означает, что полная переработка формы завершена.

## 6. Серверное подтверждение возраста, условий и передачи контактов

Реализовано 2026-10-29:

- В API новой регистрации без этих подтверждений не создаются аккаунт и сессия. Версии проверяет сервер, время берётся на сервере. Повторный вход не переписывает предыдущую запись.
- Существующий аккаунт с устаревшим подтверждением получает необходимость повторного принятия; публикация без актуальной записи запрещена и при прямом вызове API.

- Добавлены таблицы истории и миграция. Реляционная регистрация и запись согласия сохраняются транзакционно; публикация и разрешение на передачу сохраняются совместно.

## 7. Устранение уязвимой зависимости сборки API

Реализовано 2026-10-29:

- `dotnet nuget why` подтвердил цепочку: EF Design 10.0.0 → MSBuild/Roslyn → System.Security.Cryptography.Pkcs 9.0.0.
- Добавлена private-привязка System.Security.Cryptography.Pkcs 9.0.21. Это минимальный исправленный patch той же ветки, без необязательного обновления всего EF/Npgsql. Все ветки графа теперь разрешаются в 9.0.21.
- `Directory.Build.props` включает аудит прямых и транзитивных NuGet-зависимостей для API и тестов. NU1901–NU1904 становятся ошибками восстановления/сборки; предупреждения не подавляются.
- Основания: официальные [CVE-2026-84008](https://github.com/dotnet/announcements/issues/468) и [CVE-2026-70162](https://github.com/dotnet/announcements/issues/454). Обе рекомендации указывают 9.0.21 как исправленную версию ветки 9.

Проверка:

- Restore после изменения, 79/79 API-тестов без PostgreSQL integration: успешно, без NU1902/NU1903.
- `dotnet list ... package --vulnerable --include-transitive --no-restore`: известных уязвимых пакетов API по текущим источникам NuGet не найдено.
- EF migration model check: изменений относительно последней миграции нет.
- Release publish: успешно; артефакт создаётся локально в игнорируемой `.tools/release-checks/api-20261029`, не развёрнут на сервере.

Граница проверки: NuGet-аудит не подтверждает безопасность всего приложения или операционной системы. На этой машине установлен runtime 10.0.4; окружение релиза необходимо отдельно подготовить на исправленном .NET 10.0.13 или новее, пересобрать/проверить и развернуть там приложение. Системные runtime пользователя в этом этапе не изменялись.

## 10. Шесть этапов заявки и совместимость сохранённых черновиков

Оба сценария теперь состоят из шести этапов; подтверждение успешной публикации является отдельным экраном результата. Для квартиры: тип → маршрут с доступом → комнаты, коробки, вещи и дополнительные услуги → дата, бюджет и примечания → проверка → подтверждение и публикация. Для небольшой перевозки вещи заполняются перед маршрутом. Отдельные экраны доступа, фотографий и услуг объединены со связанными полями. Дополнительные услуги раскрываются по желанию, количество выбранных пунктов видно в закрытом блоке.

- Вещи показываются один раз; карточки расположены в две колонки на телефоне. Комнаты — компактная сетка; выбор комнат, вещей и услуг доступен через aria-pressed. У счётчиков коробок появились понятные названия для вспомогательных технологий.
- На последнем этапе одна кнопка публикации. Убраны процентные подписи, которые могли выглядеть как подтверждение готовности незаполненной заявки; вместо них указан текущий этап из шести.
- Замечания доступны для обоих типов перевозки. Удалена противоречивая подсказка, предлагавшая добавить фотографии при недоступной загрузке.
- Анонимный черновик формата v1 мигрирует в v2 с сохранением полей, срока действия и нового соответствующего этапа. Согласия и учётные данные не переносятся в хранилище. Новый черновик не может открыть ложный экран успешной публикации.
- Тесты покрывают оба маршрута, отсутствие повторов мебели, сохранение выбора и примечаний при переходах, перенос всех старых позиций обоих сценариев, запрет ложного результата. Всего 34 web-теста.

Это проверка браузерных размеров, не испытание на физических iOS/Android или со скринридером. Локальный API при этой визуальной проверке не запущен; корректно показан режим локального заполнения.

## 11. Проверка полей, исправление ошибок и доступные количества

Добавлена проверка основных правил заявки до отправки. Неполные черновики по-прежнему можно сохранять; отрицательные/дробные целочисленные количества, неверные этажи, отрицательные размеры, прошедшая или некорректная дата и примечания длиннее 2 000 символов требуют исправления. Перед публикацией проверяются обе адресные точки, комнаты для квартиры / хотя бы один основной предмет для небольшой перевозки, дата, временное окно и гибкость даты. Бюджет и необязательные сведения не становятся обязательными. Граница даты соответствует текущему серверному правилу UTC; это не изменение бизнес-правила календаря.

Ошибки показаны текстом рядом с полем и в списке переходов. При попытке отправки фокус переходит к первой ошибке в порядке этапов, закрытые блоки раскрываются, прокрутка происходит сразу. Исправленные ошибки исчезают без потери остальных значений. Обязательные для публикации поля отмечены явно; aria-invalid/aria-describedby связаны с сообщением. Проверка не заменяет серверную защиту или полноценный аудит со скринридером.

У мебели и специальных предметов появились редактируемые количества, у мебели — необязательные размеры и вес. Уже сохранённые специальные предметы остаются видимыми и редактируемыми после переключения на небольшую перевозку; новый каталог специальных предметов в этот сценарий не добавлен. Количество коробок больше не исправляется молча при вводе отрицательного/дробного значения: пользователь видит ошибку и своё значение.

Проверки: сценарии исправления адресов и количества, переходы из проверки, раскрытие блока доступа, сохранение значений, отдельные требования черновика/публикации, граничные даты и длина примечаний, возврат к специальному предмету после смены типа. Регрессии публикации заполняют реальные обязательные поля вместо проверки успеха на пустой заявке с замоканным API. В браузере проверены 320/390 px, фокус и отсутствие горизонтального переполнения; локальный API при визуальной проверке не запущен. ## 12. Серверная проверка Google и безопасная смена сессии

Реализовано 2026-10-29:

- Google mode использует официальную Google.Apis.Auth 1.77.0 с явно заданным audience. Проверка Google signature/issuer/expiry выполняется библиотекой; приложение проверяет subject, подтверждённый email и пределы хранения. Ожидание ограничено десятью секундами, наружу возвращаются безопасные ошибки без токенов и внутренних подробностей.
- Production не использует development verifier/SMS sender. Неверная конфигурация не переключает вход на тестовые реквизиты. Ошибки недоступных провайдеров стали структурированными 503.
- Убрано автоматическое объединение по email: другой Google subject создаёт отдельного Customer и не наследует роль или телефон существующего пользователя. Заблокированный аккаунт не получает новую сессию.
- Добавлен публичный `/api/v1/auth/capabilities`: доступность Google, публичный client ID только при доступном входе, разрешённость принятия политики и отсутствие настоящего SMS. Черновая политика продолжает закрывать production-вход.
- Исправлен обнаруженный сквозным тестом CSRF-кэш: после входа, выхода и ответа об истёкшей сессии браузер получает новый токен для текущего пользователя. Потеря ответа при смене сессии также очищает кэш. CORS разрешает cookies только явно настроенным origin.
- Добавлены сообщения ошибок входа на иврите и инструкция `docs/GOOGLE_SIGN_IN_SETUP.md`.

Локально: 112/112 обычных API-тестов, 54/54 web-теста, ESLint и Next production build прошли. NuGet audit не обнаружил известных уязвимых пакетов в текущих источниках. Дополнительно создан PostgreSQL-тест изоляции аккаунтов при одинаковом email; его реальное выполнение проверяется в CI после push.

Граница результата: браузерная кнопка пока остаётся отдельной незавершённой работой; live Google client и настоящий SMS не проверены. В сквозном тесте API заменена только граница проверки Google, остальные согласия, CSRF, сохранение пользователя и cookies выполняются настоящим кодом. Подмена валидатора в тесте не является доказательством реального входа через Google. Настройка provider credentials и финальные документы не обходятся тестовыми режимами.
